# One tab for each session: what was measured

Measured on 2026-11-18, macOS, Chrome with 10 windows, cua-driver 0.24.0, in one kept window.

| Question | Result |
|---|---|
| Does Chrome give a tab a stable id? | Yes. Apple Events (Scripting Bridge, by pid) list each tab's id, title and address. Reading them left the front app unchanged. |
| Can Accessibility read a tab that is not active? | No. The window's tree holds the active tab only. |
| Does setting `activeTabIndex` bring Chrome forward? | No. The front app stayed the same in every run. |
| Does setting a tab's `URL` bring Chrome forward? | Yes, even for a background tab. It is the last resort and the tool says when it used it. |
| Does a tab have a tree after it is shown? | A tab loaded while the tool was reading the window: yes, about 2 s after showing it. A tab loaded earlier, or unloaded by Chrome's Memory Saver: no tree after 25 s, until it is reloaded. |
| Do two Chrome windows have different frames? | Not reliably: 7 windows had one frame. A window is matched by its title and its list of tabs. |

## What the tool does with that

Each command of a tab session takes the Chrome lock, shows its tab by id, waits until the tree holds that tab's page, acts, puts the previously active tab back, and frees the lock. An agent's own tab is loaded under the tool, so it has a tree.

## Live test

Two sessions each ran `tab <window> <url>` in one window, in the background. Ten `find` commands then ran at once, five from each session: all five of each session found text that exists only on its own page, in 29 s. The window's active tab and the front app were the same afterwards. One session's `wait` left the window free for the other. A session with no tab, `use`, and `close-tab "<title>"` of another page were each refused. `close-tab` closed the session's own tab and left the other session working.
